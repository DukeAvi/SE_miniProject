# API v1 contract

`openapi.json` is the OpenAPI 3.0.3 contract for the `/api/v1` service (DOC-001; SAD Next Step 3). It includes every endpoint listed in SAD Section 4.3 plus the implemented CSRF bootstrap endpoint. The `x-implementation-status` extension distinguishes routes already mounted in Django from planned routes in the backlog; the contract does not claim that planned routes are implemented. Security and role declarations follow approved OI-4 (#87) and OI-6 (#89).

`BBMS-API-v1.postman_collection.json` contains synthetic requests generated from the same operation list. It has no account password, session value, CSRF token, or provider credential. Postman keeps the session cookie in its local cookie jar. Set demo account values only in a local Postman environment.

To use the collection locally:

1. Import the collection into Postman.
2. Set `baseUrl` to `http://127.0.0.1:8000`.
3. Set `demoEmail`, `demoPassword`, and `idempotencyKey` locally to synthetic demo-account credentials and a fresh issue-retry key; do not save them in the collection.
4. Run the `Implemented routes smoke` folder against a clean local database. It obtains a CSRF token, registers and logs in the demo account, refreshes the CSRF token after login rotates it, reads and updates the profile, then logs out. Postman retains the session cookie in its local cookie jar.
5. The `Planned endpoints` folder is contract reference material for operations with different implementation status. Check each request description before running it; replace sample query and path variables with valid local demo values.

Validate JSON structure, role/security declarations, error envelopes, idempotency, Postman parity, and all routes currently mounted in Django with:

```text
python scripts/validate_api_contract.py
```

The executable Postman smoke can be run against a clean local database and server with Newman. Set the demo values locally; do not save real credentials in the collection:

```text
npm exec --yes --package=newman -- newman run docs/api/BBMS-API-v1.postman_collection.json --folder 'Implemented routes smoke' --env-var baseUrl=http://127.0.0.1:8000 --env-var demoEmail=demo@example.invalid --env-var demoPassword='Replace-With-Local-Only-Password'
```

The current application implements the health, auth/CSRF, profile, donation slot listing, appointment booking/history/cancellation, donation recording/history, inventory create/search, Staff inventory transitions, Recipient blood-request submission, Staff request decisions, and request status/history routes. `POST /api/v1/requests` accepts the mandatory patient and requirement fields in the frozen contract. It validates the blood group, component, units, urgency, future required-by time, and contact phone; creates a uniquely numbered `PENDING` request; and records `REQUEST_SUBMITTED` atomically. The response omits patient name, hospital, and contact details. BBMS-F-030 implements DS-030 and is covered by TC-Req-01 in `tests/integration/requests/test_request_submission.py`.

`POST /api/v1/requests/{id}/decision` allows Staff to approve, reject, or hold a pending request. Reject and hold decisions require a reason. The state, reviewer, review time, protected audit event, and queued requester notification are committed in one transaction; a repeated or otherwise invalid transition returns `409` without changing the request. Delivery remains asynchronous and is handled by the notification implementation. BBMS-F-031 implements DS-031 and is covered by TC-Req-02 in `tests/integration/requests/test_request_decisions.py`.

`GET /api/v1/requests?page=1&page_size=20` returns a newest-first, paginated request list. Recipients see only their own requests; Staff can see all requests. `GET /api/v1/requests/{request_id}` returns the current status, creation and review timestamps, and a chronological status history built from protected request audit events. A foreign Recipient request ID returns the same `404` envelope as a missing ID. These read operations omit patient name, hospital, and contact phone. BBMS-F-033 implements DS-033 and is covered by TC-Req-04 in `tests/integration/requests/test_request_history.py`.

`POST /api/v1/requests/{id}/reserve` allows Staff to reserve a sufficient set of compatible, available, unexpired units for an approved request. Exact-group units are preferred; within each group, first-expiring units are selected first. The request state, allocation rows, inventory status and ledger entries, audit events, and requester notification commit together. Insufficient stock, incompatible inventory, unavailable units, or an invalid request state leave the operation unchanged. `POST /api/v1/requests/{id}/issue` issues the reserved units after rechecking compatibility, status, and expiry under row locks. It requires an `Idempotency-Key` header of 1–128 non-whitespace characters; retrying the same key for the same request returns the original successful response. BBMS-F-032 implements DS-032 and is covered by TC-Req-03 in `tests/integration/requests/test_fulfillment.py`. These are classroom-demo screening rules, not clinical transfusion guidance.


`POST /api/v1/inventory/units` accepts a completed donation UUID, scanner-friendly unit code, blood group, component, collection timestamp, expiry date, and positive `quantity_units`. Blood group and component must use the documented enums, and expiry must be after the collection date in the configured blood-bank timezone. Invalid values return field-level validation errors; database constraints enforce the enum, positive quantity, and expiry invariants. It creates an `AVAILABLE` unit and `UNIT_CREATED` audit event atomically. Use a unique alphanumeric or hyphenated code; codes are normalized to uppercase. Staff receive paginated unit-level search with independent status filtering; every result excludes units at or past expiry today. Recipients receive aggregate counts and nearest expiry only. BBMS-F-020 implements DS-020 and is covered by TC-Inv-01; BBMS-F-021 implements DS-021 and is covered by TC-Inv-02 in `tests/integration/inventory/test_unit_creation.py`; BBMS-F-022 implements DS-022 and is covered by TC-Inv-03 in `tests/integration/inventory/test_stock_transitions.py`; BBMS-F-023 implements DS-023 and is covered by TC-Inv-04 in `tests/integration/inventory/test_inventory_search.py`. Inventory stock is derived from AVAILABLE units whose expiry date is after today in the configured blood-bank timezone. Staff can discard an available unit or accept an issued-unit return through the documented transition routes; each transition locks the unit and writes its status, append-only inventory transaction, and audit event atomically. Reservation, release, issue, and scheduled expiry use the same transition service. The database enforces at most one active booking per donor and slot; cancelling an appointment releases that unique active-booking key. Donation operations use synthetic demo data, `BLOOD_BANK_TIME_ZONE` (default `Asia/Kolkata`), and `DONATION_SLOT_CAPACITY` (default 10). Booking and cancellation require a seeded donor profile and slot; staff donation recording and inventory creation require a seeded Staff account and donor profile/donation. The complete repeatable setup is tracked in QA-001 (#95).

The profile endpoint `/api/v1/users/me` always uses the signed-in account. Its GET and PATCH methods reject query parameters, including `user_id`, with `400 invalid_query`; PATCH also rejects protected or unknown body fields without saving a partial update (BBMS-F-004 / DS-004 / TC-Profile-01).

Admin account management is available at `/api/v1/admin/users`. Admin can list managed accounts, create Staff or Admin accounts, disable them, and change managed roles. Disabling an account deletes all active server-side sessions in the same transaction. `USER_CREATED`, `USER_DISABLED`, and `ROLE_CHANGED` audit rows identify the actor, target account, outcome, and time without storing credentials. BBMS-F-050 implements DS-050 and is covered by TC-Admin-01 in `tests/integration/adminops/test_staff_account_management.py`.

Protected audit search is available to Admin at `/api/v1/admin/audit-logs`. Results include the actor and role snapshot, approved action, affected record reference when applicable, outcome, source IP, correlation ID, and UTC time. Actor, action, inclusive UTC date range, affected record, and pagination filters are validated before an indexed newest-first query. See `docs/security/audit.md` for the event and data-handling rules. BBMS-F-051 implements DS-051 and is covered by TC-Audit-01 in `tests/integration/audit/test_audit_search.py`.
